# Handle an issue

For issues labelled `proposal` in `IgorLo/igorlo-llm-hub`, use the [proposal review workflow](../propose-convention/PROPOSALS.md). Other incoming feedback follows the steps below.

1. Open the [Matt Pocock triage skill](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/triage/SKILL.md) and apply its issue investigation steps. Read the discussion and prior decisions. Search for existing behavior by the user's goal, domain terms and alternative names. Check earlier rejections in `.out-of-scope/` and linked issues. Report what you found and whether the earlier reasoning still applies. For defects, reproduce on the reported version and check the integration branch. For elusive failures use [bug diagnosis](../catalog.md#bug-diagnosis). Apply tracker labels and posting conventions when the project has adopted them.
2. Trace the behavior to its owner. Inspect the application, public API, documentation and related consumers or components as relevant. Check a representative neighboring case to bound the cause. For a UI-kit report, use the kit's design review and maintenance guides for visual states, accessibility and package checks.
3. Give a disposition per issue with the evidence, owner, proposed scope and acceptance check. Options include a consumer correction, usage guidance, a component fix, a shared change, a duplicate, or a request for specific evidence. For intentional behavior or out-of-scope requests, give the reason and any supported alternative. Follow the repository's decision process. Proceed on an already agreed scope. Seek a decision when a finding materially changes it or when proposing closure without implementation.
4. When handing implementation to another agent, use the [agent brief](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/triage/AGENT-BRIEF.md) to capture the agreed behavior, scope and acceptance checks. Implement the agreed response following the [testing profile](../../profiles/testing.md). For a behavioral fix, capture the original failure in a regression check, demonstrate the corrected result and verify affected neighbors. For guidance, exercise the documented path. When reviewing the implementation against the issue, use [diff review](../catalog.md#diff-review). Link the PR and its checks, and keep separately discovered work visible with its own disposition.
5. For a fix or documentation change, confirm the PR merged into the repository's designated integration branch and that acceptance checks passed before closing. In the issue, link the integrated change and its verification. Distinguish integration, publication or deployment, and consumer retesting using the observed state of each. For an agreed duplicate or already-supported capability, link the canonical issue or demonstrate the existing behavior. For an enhancement the owner declines, follow the [out-of-scope guide](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/triage/OUT-OF-SCOPE.md): create or update one project record per concept with the rationale and related reports, then link that record when closing. For a declined bug, record the rationale in the issue. Honor the separate project workflow for any release.
